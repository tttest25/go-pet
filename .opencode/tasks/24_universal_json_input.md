# T24 — универсальный JSON-вход

**Результат.** `POST /api/v1/actions` принимает `action/version/data` и при успехе возвращает тот же 201 и те же идентификаторы, что и legacy-вход. PostgreSQL решает, можно ли поставить задание в очередь; runner получит выбранную версию в spool рядом с `tool_name`.

**Почему сейчас.** В `todo.md` T24 уже открыт первым в блоке каталога; источник приоритета — `.opencode/tasks/go_pet_actions_roadmap.md`, T24. T22 выполнен (`c4bc954`), T23 также закрыт (`9896407`), но запуск через HTTP не зависит от чтения каталога. Пользователь подтвердил маршрут, семантику оболочки, политику версий и изменение схемы. Один шаг и один коммит. T25 (выбор обработчика, формат результата), T26, T27, PHP и расширение публичных read API не входят.

## Исходное состояние и контракт

- Подтверждено кодом: `internal/api/server.go` регистрирует `GET /api/v1/actions` и `POST /api/v1/inputs`. `decodeJSON` уже ограничивает тело 1 MiB, запрещает неизвестные поля структуры и проверяет конец документа. `handleCreateInput` принимает `source/payload`; `createInputResponse` содержит `input_id,process_id,status,id`, где `id == input_id`. В `internal/api/server_test.go` есть `TestCreateInput`, `TestCreateInputValidation`, `TestCreateInputDatabaseError`, `TestCreateInputPayloadIntegration`; в `internal/api/timeouts_test.go` — `TestHTTPDatabaseTimeout`.
- В `postgres/migrations/000005_action_catalog.up.sql` `sm_create_input` проверяет `sm_validate_tool_payload` и активную **v1** по `payload.tool`; триггер из `000002` создаёт процесс и job с тем же payload. Активная строка каталога сама по себе не устанавливает валидатор. `internal/db/queue.go:PickNextJob` сканирует шесть полей `sm_pick_next_job()`, `internal/spool/writer.go` собирает отдельный `jobDocument`: ни там, ни в `sm_jobs` версии задания нет.
- Новый маршрут: клиент не задаёт `source` (в БД всегда `api`). Требуются непустое, не состоящее из пробелов строковое `action` с точным сравнением имени, JSON-целое `version` в диапазоне 1…2147483647 и ключ `data`. Ограничение тела, один документ, неизвестные поля оболочки и ошибки — в стиле legacy. Нет `data` → HTTP 400 до БД. Есть `data`, даже `null`, строка, число или массив → передать исходное JSON-значение как `json.RawMessage`, не декодировать в `any`, не делать `Marshal` и не проверять тип в Go. Побайтовая проверка относится к границе Go → DB-метод, не к хранению в JSONB.
- PostgreSQL принимает для трёх v1 только объект данных без верхнеуровневого ключа `tool` (даже совпадающий или `null` запрещён). Внутренний payload — данные плюс доверенный `tool` из `action`. Прежние правила полей и defaults: `{}` допустим для echo; лишние поля данных сохраняются, `fabric.text` и `yt-dlp.url` обязательны. Неизвестная/выключенная пара, v2 даже при `enabled=true` без реализованных правил, `null`/необъект или плохие поля → `22023` → HTTP 400, без новых input/process/job. Внутренние ошибки → 500, истечение собственного DB-бюджета → 504 согласно T19.
- `sm_jobs.action_version integer NOT NULL DEFAULT 1` с проверкой положительности; уже созданные jobs и новые legacy jobs получают 1. В spool рядом с `tool_name` обязательна числовая `action_version`; версия не берётся из данных клиента. Ответ 201 и ответы существующих GET не расширять. Runner в T24 не меняется.

## Реализация по TDD и приёмка

Ни тесты, ни миграция в Plan не запускались. Ниже **ожидаемые**, а не полученные RED. Для каждой группы сначала зафиксировать результат теста; ошибка окружения не подтверждает RED. Уже зелёные legacy-проверки использовать как регрессию.

1. **Первый тест — `internal/api/server_test.go:TestCreateActionForwardsRawData`.** Через существующий `newServer`/`httptest` отправить `POST /api/v1/actions` с `action:"echo-test"`, `version:1` и объектом `data`, содержащим внутренние пробелы, дополнительное поле с большим целым и строку с JSON-escape. В тестовом fake заранее объявить метод `CreateAction(ctx, action, version, data)` и запись аргументов, не меняя production-интерфейс до RED. Проверить сначала HTTP 201 (сейчас ожидается **405**, есть только GET), затем четыре поля ответа, `id == input_id`, `status == "new"`, один вызов с точными именем, версией и байтами `data`, ноль legacy-вызовов. GREEN: зарегистрировать POST, добавить DTO с `int32` и **неуказательным** `json.RawMessage`, метод `databaseAPI`, тонкий `DB.CreateAction` с параметризованным вызовом предлагаемой `public.sm_create_action(text,integer,jsonb)` и сканированием `CreatedInput`; переиспользовать формат ответа и бюджет БД. Fake-тест не доказывает готовность SQL.
2. **`TestCreateActionEnvelope` и `TestCreateActionErrors`.** Таблица: пустое/битое/второе JSON, тело больше лимита и корректное на границе, не объект, лишний `source`, отсутствующий `data`, пустое/нестроковое имя, пропущенная/нулевая/отрицательная/дробная/строковая/переполненная версия. Для ошибок оболочки — JSON 400 и ноль DB-вызовов. В отдельной группе присутствующий `null`, массив, число, строка → fake видит именно эти байты и может вернуть `ErrInvalidInput`; не путать с отказом транспорта. Ожидаемые пробелы после happy path — пропущенные поля, неверное различение `nil` и `"null"`, неверный статус ошибки. GREEN: `decodeJSON`, явные проверки обязательности/диапазона без списка инструментов. Расширить `TestHTTPDatabaseTimeout` новым POST: свой дедлайн → 504, прочий сбой → 500 без внутренних деталей; использовать логику T19. Сохранить старые POST/GET тесты.
3. **`internal/db`: `TestCreateActionContract`.** На подготовленной `petar_test` проверить SQL-функцию напрямую: успехи для каждой v1 (включая echo `{}`), `source='api'`, возвращённые UUID связывают ровно один input, один process и один pending job; payload с доверенным tool и исходными полями. В транзакциях проверить отключённую v1, неизвестное имя, незарегистрированную и зарегистрированную активную v2, JSON `null`, прочие необъекты, `data.tool`, неверные поля каждого инструмента. Ошибка именно `22023`; под savepoint откатить ошибочный statement и сравнить количества всех трёх таблиц с baseline, изменения каталога откатить. Ожидаемый RED на схеме 000005 — отсутствующая функция, а не отсутствующая БД. GREEN: новая пара `postgres/migrations/000006_universal_json_input.{up,down}.sql`. В новой функции сначала проверить поддерживаемую версию и форму данных, затем передать в существующую `sm_create_input('api', …)` собранный в SQL payload: это переиспользует проверку активной v1, существующий валидатор и единственный триггер создания цепочки. Не менять legacy-функцию и не создавать вторую цепочку. Сопоставить `22023` с `db.ErrInvalidInput` с сохранением причины, не с ошибкой callback.
4. **Версия до файла.** В DB-тесте проверить тип, NOT NULL, default и положительность `action_version`; в `internal/spool/spool_test.go` дополнить `TestWriteJobCreatesJSON` проверкой числа, передав в writer тестовую версию, отличную от 1. В `TestSpoolWorkerIntegration` проверить версию в опубликованном JSON против строки БД (для проверки переноса, а не константы, допустима отдельная контролируемая SQL-фикстура с версией 2, без запуска действия v2). Без изменения схемы/диспетчера/проекции текущий код не даст колонку/ключ. GREEN: добавить колонку в 000006; для единственной разрешённой версии 1 default корректен и для нового, и для legacy-входа. Вернуть фактическое значение в `db.Job` и `jobDocument`, сохранить атомарный writer. Минимальный вариант без смены сигнатуры старой функции: в `pickNextJobQuery` явно выбрать шесть полей результата функции и `j.action_version`, соединяя со `sm_jobs j` только по возвращённому id, в том же SQL statement. Статусы брать из результата функции, версию — из строки; сохранить выбор/блокировку и `nil` для пустой очереди. Не превращать worker в валидатор версий.
5. **HTTP + настоящая БД:** `TestCreateActionIntegration` рядом с `TestCreateInputPayloadIntegration`: новый POST → 201, действительная связанная цепочка, версия и payload; выключенная v1 / активная v2 / `data:null` → 400 с неизменными счётчиками; legacy echo с прежним `source` всё ещё 201, тот же формат, job v1. Использовать штатный guard и cleanup, не общий spool. Эти тесты выявляют ошибки связывания pgx/JSONB, SQLSTATE и HTTP, невидимые fake-тесту; исправлять на соответствующей границе, не подгонять fake. Сохранить отдельное поведение `GET /api/v1/actions`: видимость активной v2 не обещает установленный валидатор.
6. **Lifecycle и rollback:** начать с ожиданий схемы/порядка в `internal/db/test_lifecycle_test.go`, `internal/db/test_guard_test.go` и пробе `scripts/check-fresh-bootstrap.sh`: старая схема не содержит новой функции/колонки. Обновить явный up-список, check и smoke; fresh bootstrap должен пережить алфавитный запуск `.down.sql` перед `.up.sql` на чистом PGDATA (down безопасен при отсутствии объектов T24). Проверить up → down → up 000006 на отдельной одноразовой БД, включая данные и legacy; не переигрывать 000002 на существующей схеме. Актуализировать `README.md` и `architecture.md`: маршрут, примеры, ошибки, различие каталога и поддержки, миграция и поле spool.

## Команды Build (последовательно из `/opt/go-pet`)
