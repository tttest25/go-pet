# T26 — Чтение публичного результата по job_id

**Результат.** Клиент сможет получить публичный JSON конкретного завершённого задания по его UUID, в том числе когда в процессе несколько заданий. Пока результат не готов, при неудаче задания или потере файла клиент получит различимые ответы без внутренних путей и диагностик runner.

**Приоритет и границы.** `todo.md`: T22–T25 закрыты, T26 открыт; `.opencode/tasks/go_pet_actions_roadmap.md`: T26 зависит от T25, T27 ждёт T26. Пользователь подтвердил контракт целиком. Один шаг: чтение в Go, тесты, документация API/эксплуатации. Схема, миграции, запись файлов и callbacks, прежние GET, перегенерация старых результатов, PHP и word-count вне задачи.

## Исходная точка (проверено по исходникам)

- `scripts/spool-runner.sh:publish_public` публикует временный файл через rename в `out/<job_id>/public.json` до completed. Callback указывает на другой файл — `/spool/out/<job_id>/result.json`. `scripts/spool_runner_test.go`: `TestRunnerPublicEcho`, `TestRunnerPublicFabric`, `TestRunnerPublicYTDLP`, `TestRunnerStalePublicResult` покрывают публикацию, не HTTP-чтение.
- `internal/api/server.go:newServer` не регистрирует GET результата. `handleGetProcess` и `handleListJobs` возвращают метаданные; `internal/db/queue.go:ListJobs` не является точечным чтением статуса. `cmd/petar/main.go:run` передаёт `cfg.SpoolDir` writer, но не API. Нужны запрос по PK, доступ к тому же spool и новый маршрут.
- `internal/api/server_test.go` уже имеет `performRequest`, `newActionsIntegrationServer` с настоящими `db.DB` и verification pool через `requireTestDSN`, `fakeDatabase` и пример `TestListJobsHasDatabaseDeadline`. Использовать существующий guard. Планировщик тесты не запускал; ниже RED — прогноз, не результат.

## Контракт и проверяемая приёмка

`GET /api/v1/jobs/{id}/result`, JSON. Источник состояния — `SELECT status FROM public.sm_jobs WHERE id=$1`. Только для completed читать `SPOOL_DIR/out/<uuid.String()>/public.json`. Не использовать строку URL как часть пути, `result_path`, `error_msg`, process outputs, текущий каталог действий или поиск по процессу.

| Условие | Ответ и проверка |
|---|---|
| Неверный UUID / неизвестный UUID | 400 до БД / 404 даже при наличии файла. Нейтральный JSON `error`. |
| pending, dispatched, in_progress | 202, только `{"status":"<фактический статус>"}`; наличие уже опубликованного файла не даёт 200. |
| failed | 409 `{"error":"job_failed"}`, даже если остались файлы; без текста `error_msg`. |
| completed, валидный файл до 1 МиБ включительно | 200, сам JSON T25: один UTF-8 объект, ровно `type` (непустая строка), `version` (число 1 для формата T25), `data` (объект). Внутренние поля data доверены runner, без Go-списка действий и повторной валидации каждого инструмента. Два job одного процесса возвращают каждый свой документ. |
| completed, файл/каталог job отсутствует | 410 `{"error":"result_unavailable"}`; то же для legacy без public.json, без fallback на result.json. |
| completed, повреждение оболочки или ошибка чтения | 500 с нейтральной JSON-ошибкой, без фрагмента файла/системной причины. |
| Более 1 048 576 байт | 500 `{"error":"result_too_large"}`. Проверить размер по прочитанным байтам, включая whitespace; ни части документа, ни предварительного 200. |
| Ошибка БД | По образцу `handleGetProcess`: собственный истёкший DB-бюджет при ошибке → 504; обычная ошибка → 500 без причины; более ранняя отмена клиента не становится серверным 504. |

## RED → минимальный GREEN

1. **Начать с `internal/api/server_test.go:TestGetJobResultSelectsRequestedJob`.** В тестовом helper использовать существующий `newActionsIntegrationServer` (можно обернуть, передав `root := t.TempDir()` в тестовую фабрику; на RED оставить реальный старый конструктор). Через verification pool создать input штатной функцией, получить созданный job A, вставить job B с тем же process_id; довести оба до completed в зафиксированной фикстуре. Удалить собственный input через `t.Cleanup` с каскадом. В `root/out/<A|B>/public.json` записать два разных echo-документа; в соседний `result.json` записать приватный маркер, в callback/result_path задать вводящий в заблуждение путь. Дважды вызвать настоящий Handler и проверить статус, Content-Type и весь документ соответствующего job. До изменений компилируемый тест должен получить **404 вместо 200**. Ошибка подключения или создания фикстуры не является RED.
   - GREEN: один точечный метод `GetJobStatus(ctx, id)` в `internal/db/queue.go` и `databaseAPI`, `Scan` в `db.Status`, обёртка ошибок с `%w`; адаптировать fake. Зарегистрировать GET, передать `cfg.SpoolDir` из main при сборке сервера, тестовой фабрике — явный temporary root, без глобального рабочего spool. Для completed открыть только вычисленный файл и вернуть документ. Сразу читать с верхней границей, не вводить промежуточную неограниченную раздачу файлов. Новые функции I/O принимают `ctx` первым аргументом.
2. **`TestGetJobResultStates`**: таблица всех остальных статусов, 400 без запроса, отсутствие строки (включая orphan public.json), failed с секретным маркером, нетерминальные состояния при готовом файле. Прежде одной успешной ветки недостаточно; GREEN — разбор UUID, ветвление по `status`, `errors.Is(err, pgx.ErrNoRows)`; выход до любого файлового чтения, точные JSON-ответы по таблице. Один сценарий 404 проверить через реальную БД, чтобы проверить поведение `Scan`/обёртки.
3. **`TestGetJobResultFileErrors`**: legacy-каталог только с result.json/stderr.log → 410; отсутствует каталог job → 410; вместо файла каталог, повреждённый JSON, неверный UTF-8, второй документ, лишнее/пропущенное поле, неверные типы → 500 без выдачи содержимого. Отдельно проверить ссылку на внутренний файл и подмену каталога job ссылкой: не раздавать чужой файл. Простая выдача байтов не различает эти случаи. GREEN — из доверенного spool открыть каталог out, каталог UUID и обычный файл без перехода по ссылкам (на Linux можно использовать открытие относительно дескриптора с `O_NOFOLLOW`, для файла неблокирующее открытие и `fstat`). Закрывать дескрипторы; различать отсутствие и иные ошибки. Проверять **весь** буфер и точные ключи публичной оболочки до записи ответа. Не фильтровать произвольный легитимный пользовательский текст в data. Для ошибки чтения использовать воспроизводимую фикстуру, не полагаться на chmod под root.
4. **`TestGetJobResultSizeLimit`**: валидные документы ровно 1 МиБ и на байт больше (удобно дополнить пробелами), уникальный маркер внутри. Проверять реальную длину тела на границе, отсутствие маркера и точную ошибку при превышении. `LimitReader` без контрольного байта не отличает переполнение; `json.Encoder` может добавить байт. GREEN — `io.LimitReader(file, limit+1)`, проверка переполнения до JSON-валидации и любых заголовков успеха; отдать проверенные байты как `application/json; charset=utf-8` без повторной сериализации. Если ограничение введено в первом GREEN, зафиксировать фактически зелёный граничный тест, не имитировать RED.
5. **`TestGetJobResultDatabaseDeadline`**: fake наблюдает дедлайн, ожидает отмены в тесте с укороченным серверным бюджетом, отдельно возвращает обычную ошибку или видит отмену родителя. GREEN — существующие `context.WithTimeoutCause` и `writeDatabaseTimeout` только для неуспешного SQL-вызова. Читать файл с контекстом запроса, не трактовать файловый сбой как DB timeout. Ранее реализованные исходы прогонять как регрессию.
6. Обновить `README.md` и `architecture.md`: пример GET по job UUID, таблица ответов, включительный предел, различие `result_path` и `public.json`, старые completed без файла. Заменить устаревшие утверждения «Go не читает out». Отметить, что UID app должен иметь доступ к публикации runner (`mktemp`); не расширять права на весь spool.
