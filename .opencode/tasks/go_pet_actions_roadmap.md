# go-pet: каталог действий и универсальное выполнение

Согласованная дорожная карта для `/opt/go-pet/todo.md`. Пункты переносить открытыми, по ID, не дублировать. Один шаг — один атомарный коммит после приёмки. Согласование карты разрешает планирование согласованной схемы T22, но не заменяет финальный Human Sign-off.

- [ ] **T22: Каталог действий в PostgreSQL.** Хранить идентификатор, версию, название и признак доступности. Начальные записи — `echo-test`, `yt-dlp`, `fabric` версии 1. Проверять доступность в пути `sm_create_input` до вставки. Валидный ввод создаёт одну цепочку; неизвестное или отключённое действие → `22023`, без input/process/job. Старый формат и правила трёх инструментов сохраняются. Проверить обратимость миграции на одноразовой БД.
- [ ] **T23: API чтения каталога.** `GET /api/v1/actions` читает доступные действия и версии из PostgreSQL. Новая запись видна без изменения Go-списка; отключённая исчезает из выбора, но не из истории заданий. Зависит от T22.
- [ ] **T24: Универсальный JSON-вход.** Go ограничивает размер тела, принимает один JSON-документ, проверяет оболочку `action/version/data`, передаёт значение `data` без повторного кодирования. Отсутствующее `data` отличается от `null`; допустимые типы и поля определяет PostgreSQL. Невалидный JSON → 400 без обращения к БД; отказ БД → 400 без новых строк; успех → 201. Сохранить прежний `POST /api/v1/inputs` и формат успешного ответа. Зависит от T22; T23 не требуется для прямого API-теста.
- [ ] **T25: Контракт обработчика и публичного результата.** Runner выбирает установленный обработчик по имени и версии; результат — публичный JSON с типом и версией. Старые задания совместимы. На echo проверить значение; недоступный обработчик или невалидный вывод → failed, без ложного completed. Пути, stderr и произвольные команды хоста не являются публичным контрактом. Согласовать передачу версии из T24.
- [ ] **T26: Чтение публичного результата по job_id.** Различать неготовое, успешное, ошибочное и отсутствующее задание. Для двух заданий одного процесса выдавать результат только запрошенного job; ограничить размер ответа и исключить внутренние пути/логи. До реализации закрепить статусы HTTP, источник привязки job → результат и политику превышения размера. Зависит от T25.
- [ ] **T27: Доказательство расширяемости на word-count.** Зарегистрировать действие с валидатором и обработчиком. `{"text":"один два три"}` → `{"words":3}` без изменения HTTP-обработчиков и кода плагина под это действие. Backend-проверка после T22–T26; сквозная приёмка в wiki после PHP-06/07.

## Первая итерация: T22

1. Начать в `internal/db` с нового `TestActionCatalogInitialEntries`: на подготовленной изолированной `petar_test` запросить из предлагаемой `public.sm_actions` активные `(action, version)` и проверить три согласованные пары. Ожидаемый RED — отсутствует таблица, не ошибка DSN/подготовки. RED при подготовке карты не запускался.
2. Минимальный GREEN: новая пара `postgres/migrations/000005_action_catalog.{up,down}.sql`, ключ `(action, version)`, начальные записи. Обновить явный список миграций и его тест в `internal/db/test_lifecycle_test.go`; проверить проверки схемы, fresh-bootstrap и документацию, завязанные на старый набор. Не применять старые миграции повторно поверх подготовленной схемы.
3. Следующий RED: в изолированной транзакции отключить `echo-test` v1, под savepoint вызвать `sm_create_input` с корректным legacy payload; ожидать `22023`. После отката до savepoint проверить отсутствие новых строк, всю транзакцию откатить. Без проверки каталога функция пока примет задание. GREEN: проверка активности legacy v1 внутри штатной функции до вставки, в той же транзакции. Сохранить `sm_validate_tool_payload` и ошибку для неизвестного действия.
4. Проверить совместимость через существующие `TestCreateInputPayloadContract`, `TestCreateInputPayloadIntegration`, включая echo без message; отключение не меняет существующие jobs. Проверить `up → down → up` на отдельной одноразовой БД; down восстанавливает поведение 000004 и не удаляет задания. Не использовать рабочую БД или общий spool.
5. Из `/opt/go-pet` с работающим PG18 и явным `PETAR_TEST_DB_DSN` штатной отдельной `petar_test`: `./scripts/test-db.sh prepare`, `./scripts/test-db.sh check`, целевой `go test -p=1 -count=1 -race ./internal/db -run 'TestActionCatalog|TestCreateInputPayloadContract'` до/после изменений. После миграции явно подготовить и проверить схему разрешённым lifecycle; при несовместимом состоянии использовать отдельный чистый контур, не выполнять неявный reset. Затем `go test -p=1 -count=1 -race ./internal/api -run TestCreateInputPayloadIntegration`, `go build ./...`, `GOFLAGS=-count=1 ./scripts/quality-gate.sh`. Проверить fresh bootstrap при изменении его ожиданий. Gate включает vet/race. Независимый review схемы, совместимости и обратимости → diff и результаты пользователю → Human Sign-off → атомарный коммит.

Не включать API каталога, новую оболочку, изменение runner или PHP в T22. Согласовать отдельно любое расширение области.
