### Strict TDD и наблюдаемая приёмка

Для каждого нового контракта сначала запускать узкий тест на предыдущей реализации, сохранять фактический RED (нарушение поведения, не ошибка fixture), затем минимальный GREEN. Ниже прогнозы, не результаты. Уже работающие случаи использовать как контроль, не ломать их ради RED.

1. **Начать с `TestRunnerMissingCLI/yt-dlp`.** `t.TempDir()` для spool, валидное `<uuid>.json` в `in` с `id`, `tool_name:"yt-dlp"`, `payload:{"tool":"yt-dlp","url":"https://example.org/v"}`. Вызвать настоящий `bash ./spool-runner.sh` из пакета scripts через `exec.CommandContext` с внешним дедлайном. Изолированный PATH: ссылки на реальные необходимые Bash/утилиты (в т. ч. jq, coreutils, flock), fake curl, **без наследования** установленных yt-dlp/fabric или настоящего curl. Fake пишет URL и JSON каждого POST отдельно, возвращает 204 согласно `-w`, не обращается в сеть. Проверить последовательность `in_progress,failed`, `error_msg` называет отсутствующий CLI, нет completed/simulated artifact, после подтверждённого failed в processing пусто. Ожидаемый RED: второй POST `completed`. Убрать simulated-ветку, направить отсутствие CLI в существующую ветку ошибки. Повторить для `fabric` с валидным text. Принятый `failed` — штатное завершение обработки файла, в отличие от ошибки доставки callback.
2. **`TestRunnerCallback`**: параметризованный fake curl на первом и терминальном POST (для терминального проверить completed и failed). Проверять точный 204 + exit 0, отказ на 200, redirect 302, 500, exit != 0 (включая «код 204 напечатан, транспорт неуспешен»), наличие конечных положительных `--connect-timeout` и `--max-time`, отсутствие follow/retry. RED: 302 проходит; сетевой сбой не гарантированно распознан; флагов нет. GREEN: явно отдельно проверять exit curl и строку кода, игнорировать тело, не выводить тело/секреты. При любом неподтверждённом POST выход с ошибкой, файл **остаётся** в processing; диагностика указывает job, этап и необходимость проверить БД перед ручным решением. На первом сбое CLI не запускался, на терминальном уже выполненный CLI не повторять, артефакты оставить. Проверить счётчиком запусков и вторым обычным проходом, что нет нового CLI/POST. Удалять только после подтверждённого terminal 204. Согласованный backend не менять.
3. **`TestRunnerToolExecution`**: fake CLI записывают реальные argv с границами и stdin, раздельные stdout/stderr с маркерами. Проверить успешный `echo-test` (включая default), `yt-dlp --dump-json -- "$url"` с query и `&`, `fabric --pattern "$pattern"` (явное значение и default `summarize`), текст с кавычками, начальным `-`, несколькими строками и конечными переводами строк. Проверять содержимое артефактов и прежний completed.result_path `/spool/out/<id>/result.json`. RED — нет `--`, text меняется через `echo`/подстановку, stderr в общем логе. GREEN — отдельные quoted argv, передать text через stdin без shell-интерпретации и потери байтов (например, `jq -j` непосредственно в stdin); stdout CLI сохранить как прежде, stderr отдельно внутри `out/<uuid>/`, также при ошибке. При nonzero сохранить оба потока для диагностики, отправить только `failed` с краткой причиной/кодом. Проверить, что контрольный секрет из text, URL или stderr отсутствует в логах runner и `error_msg`. Не использовать `eval`/`sh -c` для входных данных.
4. **`TestRunnerToolTimeout`**: fake CLI зависает, в том числе игнорирует TERM; ограничить время теста с запасом, предусмотреть cleanup дочерних процессов. RED — нет `failed` до внешнего дедлайна. GREEN — GNU `timeout` с конечным grace и kill-after, обработать timeout как `failed` с понятной причиной, сохранить доступный вывод, убрать processing только при 204. Вариант реализации для воспроизводимого теста: положительные целые секунды `RUNNER_TOOL_TIMEOUT` (по умолчанию 300, в тесте 1), grace 1 с, для curl connect/max 3/10 с. Это предлагаемые локальные параметры, не значения из дорожной карты; не разрешать нулевое/невалидное значение отключить ограничение. Проверить наличие нужных host utilities до захвата заданий.
5. **`TestRunnerInvalidJob`**: невалидный JSON, отсутствующий/неканонической формы UUID и id с разделителем пути — без callback, CLI, удаления или создания выхода по данным документа; при переносе использовать только имя входного файла, сохранить его для разбора. RED — удаление при отсутствующем id либо обращение по непроверенному id. GREEN — проверить форму UUID (не ограничивать только v7) до построения URL/путей по id. Для валидного id, но испорченных аргументов, подтвердить `in_progress → failed`, ноль запусков CLI. Таблично проверить типы, blank/null против отсутствия, pattern `[A-Za-z0-9_-]{1,128}`, абсолютный HTTP(S) URL с host (в т.ч. отрицательные случаи — option вместо URL, пустой host, пробелы), допустимые tool. Не превращать типы через `jq -r` до проверки, не нормализовать валидные строки. Минимальная защита на границе Bash; SQL остаётся каноническим валидатором.
6. **`TestRunnerSpoolLock`**: первый процесс `--loop` сообщает о входе в fake CLI и ждёт управляемого сигнала; затем положить второе задание, запустить второй runner на том же spool. RED — второй может забрать новое задание. GREEN — неблокирующий `flock` на постоянном lock-файле данного spool до сканирования, держать один FD весь проход/цикл; второй быстро выходит с диагностикой, файл остаётся в `in`. Подтвердить освобождение после выхода владельца и последующий успешный захват; синхронизировать процессами/сигналами готовности, а не произвольным sleep. Уложить весь пакет в timeout gate 30 с.
7. Обновить README (зависимости, таймауты, результаты/диагностика, single runner и ручная сверка состояния по job ID при неясном ответе); убрать устаревшие simulated-инструкции и точечно согласовать §5 архитектуры. Не обещать автоматический retry, exactly-once или возможность повторить действие по одному сетевому коду.
