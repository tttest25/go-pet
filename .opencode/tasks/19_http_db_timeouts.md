# T19 — Ограничить ожидание HTTP и БД

Основание: `todo.md` закрывает T16–T18; `.opencode/tasks/16_phase1_hardening_plan.md` (§ T19, протокол в конце файла) ставит этот шаг перед T20. Один шаг, один коммит. Численные пределы и область действия утверждены пользователем.

## Контракт и исходное состояние

| Граница | Проверено в коде | Результат T19 |
|---|---|---|
| HTTP transport | `cmd/petar/main.go:67–76`: `ReadHeaderTimeout=5s`, `IdleTimeout=60s`; `ReadTimeout` и `WriteTimeout` не заданы | Сохранить первые два, установить `ReadTimeout=15s`, `WriteTimeout=20s`. Это пределы операций транспорта, не таймер выполнения Go-обработчика. |
| HTTP → БД | `internal/api/server.go`: `GetProcess`, `ListJobs`, `Ping`, `CreateInput`, `UpdateJobStatus` получают `r.Context()` напрямую | От момента обращения к БД дать до 5s на вызов метода целиком, включая ожидание соединения. Наследовать значения, отмену и более ранний дедлайн запроса. Нет нового ENV. |
| Ошибки | Есть `writeError`, readiness 503, предметные ошибки 400/404 и обычные ошибки 500 | Если вызов завершился ошибкой из-за серверного DB-дедлайна и соединение доступно, четыре API-операции возвращают JSON 504, `Ping` — существующий JSON 503. Не превращать отмену клиентом или обычную сетевую ошибку в серверный 504. Успешный результат не заменять ошибкой по поздно сработавшему таймеру. |
| Остановка | `cmd/petar/main.go:126–149`: `Shutdown` с лимитом 10s, при ошибке `Close`, затем остановка worker | Сохранить порядок и 10s. Проверить, что активный запрос, ожидающий БД, отпускает сервер при штатном завершении. |

Вне шага: глобальный таймаут пула, изменение SQL/схемы, `LISTEN`, worker, runner и его HTTP-клиент, новые пакеты. Лимит размера тела и существующая валидация сохраняются. 504 при мутации не доказывает откат и не означает, что её можно автоматически повторить.

## Реализация от тестов

Ниже ожидаемые, а не наблюдавшиеся RED: на этапе Plan код не менялся, тесты не запускались. Для каждого нового поведения сначала запустить тест на прежней реализации, сохранить причину RED, затем минимальный GREEN. Уже работающий контракт достаточно подтвердить регрессией.

1. **Начать с `internal/api/server_test.go::TestListJobsHasDatabaseDeadline`.** На основе `newFakeDatabase`, `newServer`, `performRequest` вызвать `GET /api/v1/jobs` без дедлайна родителя. Зафиксировать время до/после вызова; проверить `200` и что `f.listJobsContext.Deadline()` существует и лежит между этими отметками плюс 5s. Это проверяет production default без ожидания пяти секунд. Ожидаемый RED: `ok == false`, fake получил контекст запроса напрямую. GREEN: добавить закрытый параметр длительности у `api.Server`, инициализировать `5*time.Second` в `newServer`, ограничить вызов `ListJobs` дочерним контекстом, сразу предусмотреть `defer cancel()`. Публичный конструктор оставить прежним.
2. **Реальное истечение DB-бюджета.** Добавить `TestHTTPDatabaseTimeout` с отдельным fake на случай: при входе в метод дождаться `ctx.Done()` и вернуть обёрнутую ошибку. Без предоставленного дедлайна fake должен немедленно зафиксировать нарушение, а не зависнуть. Через тестовый экземпляр `Server` до первого запроса задать короткий бюджет (например, 50ms); не менять глобальные переменные. Проверить сначала `ListJobs`, затем таблицей `GET /api/v1/processes/{валидный UUID}`, `POST /api/v1/inputs` с валидным echo-test, `POST /api/v1/jobs/{валидный UUID}/status` с `in_progress`, `GET /readyz`. Проверять вызванный метод, факт истечения контекста и JSON-ошибку: 504 в первых четырёх API-сценариях, 503 для readiness. Одного статуса 503 недостаточно: он уже возвращается при любой ошибке `Ping`. Ожидаемый RED: 500 у ограниченного, но ещё не различающего ошибки обработчика; отсутствие дедлайна у остальных.
   - GREEN: создавать ограниченный контекст непосредственно перед каждым вызовом, после проверки параметров/декодирования тела. Для различения своего дедлайна и чужой отмены подходит `context.WithTimeoutCause` с приватной причиной; проверять причину при ошибке вызова, не полагаться на текст ошибки pgx. Оставить существующие ветки `db.ErrInvalidInput`, `pgx.ErrNoRows` и обычных ошибок, если собственный лимит не истёк. Не запускать DB-вызовы в фоновых горутинах ради таймаута.
   - Проверить более ранний дедлайн родителя: fake видит тот же момент окончания, а не новый срок в 5s. Для отменённого клиентом запроса проверить распространение отмены, не обещать доставку ответа на закрытое соединение. Сохранить `testReadContext`: тест уже проверяет значение контекста и отмену; fake, который вернул успех, должен по-прежнему получить 200. Прогнать существующие проверки успешных запросов и ошибок (включая `TestCreateInputDatabaseError`, `TestUpdateJobStatusDatabaseErrors`, `TestGetProcess`, `TestListJobs`, `TestReadyz`).
3. **Транспорт и медленное тело.** В `cmd/petar/main_test.go` тестировать тот же `http.Server`, который запускает `run()`. Допустим подготовительный механический вынос существующего литерала в приватный конструктор без изменения полей: тогда RED теста настроек — фактические `0/0` вместо `15s/20s`, а не только отсутствие символа. Проверить все четыре production-значения. В поведенческом тесте поднять сервер на локальном listener; оставить заголовки полными, объявить `Content-Length`, записать только часть тела и **не закрывать** клиентскую сторону записи. Handler сигнализирует вход в чтение и возвращает его ошибку в канал. Уменьшить только уже настроенный ненулевой ReadTimeout у тестового экземпляра (нулевой оставить нулевым, чтобы тест ловил регрессию). До внешнего watchdog чтение должно завершиться по серверному timeout; с нулевым лимитом watchdog завершает тест ошибкой. Cleanup закрывает соединение и сервер. Не считать успехом клиентский timeout, не проверять текст ошибки или наличие JSON после обрыва. GREEN: установить недостающие поля в production-конструкторе, подключённом к `run()`.
4. **Graceful shutdown при активной операции.** Добавить поведенческий тест в `internal/api` с реальным `http.Server` и настоящим API-handler на fake DB: запрос `GET /api/v1/jobs` дошёл до fake (сигнал `entered`), соединение активно, инициировать `Shutdown` с ограниченным контекстом. Синхронизировать старт shutdown, например через `RegisterOnShutdown`; удерживать fake до этого сигнала и `ctx.Done()`. Проверить, что запрос получил JSON 504, `Shutdown` вернул nil без принудительного закрытия, serving goroutine завершилась штатно. Короткий DB-лимит, запас на shutdown больше его и на внутренний опрос `net/http`, внешний watchdog и cleanup всех соединений/каналов. Не подменять активную операцию мгновенным ответом fake. Это проверка нового DB-лимита вместе с существующим механизмом остановки; если после шагов 1–3 зелёная сразу, отдельное изменение shutdown не требуется.
5. **Документация.** В `architecture.md` (HTTP-контракты и shutdown) и `README.md` (HTTP/эксплуатация) синхронизировать пять чисел, 504/503 и отличие DB-дедлайна от обрыва транспорта; указать, что для медленного тела JSON не гарантируется. Не добавлять ENV в таблицы конфигурации. В `todo.md` добавить пункт ниже, пока `[ ]`.

## Проверки и свидетельства

Рабочий каталог всех команд — `/opt/go-pet`. Использовать доступный `petar_postgres`, только изолированную `petar_test`. Перед тестами (в том же shell, где они будут запускаться):

```sh
export PETAR_TEST_DB_DSN='postgres://petar_user:petar_password@127.0.0.1:5432/petar_test?sslmode=disable'
./scripts/test-db.sh check
```

Если изолированная БД ещё не подготовлена, выполнить `./scripts/test-db.sh prepare`, затем `check`; при другой ошибке выяснить причину. Не сбрасывать БД и не подменять DSN рабочей базой. Запускать проверки последовательно из-за общего lock.

```sh
# Первый тест — отдельно и до изменения логики; повторить после изменения.
go test -count=1 -v ./internal/api -run '^TestListJobsHasDatabaseDeadline$'
# При добавлении каждого сценария — адресный RED/GREEN; затем вместе:
go test -count=1 -v -race ./internal/api -run 'Test(ListJobsHasDatabaseDeadline|HTTPDatabaseTimeout|HTTPShutdownWithActiveRequest|GetProcess|ListJobs|Readyz|CreateInputDatabaseError|UpdateJobStatusDatabaseErrors)'
go test -count=1 -v -race ./cmd/petar -run 'TestHTTP(ServerTimeouts|SlowRequestBody)'
go build -o /tmp/opencode/petar-t19 ./cmd/petar
GOFLAGS='-count=1' ./scripts/quality-gate.sh
```

Имена новых тестов использовать как в командах. Gate (`internal/db/test_lifecycle_test.go`) уже запускает `go vet ./...` и полный `go test -p=1 -count=1 -v -race -timeout 30s ./...`; сохранить фактический вывод и статус каждой стадии. Не выдавать пропуск/инфраструктурный сбой за PASS.
